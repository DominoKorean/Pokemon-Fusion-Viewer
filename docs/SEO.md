# Search discovery and link previews

[한국어 안내](SEO.ko.md)

The production URL is **https://dominokorean.github.io/Pokemon-Fusion-Viewer/**. It is configured in `src/seo.mjs`; metadata and sitemaps use that value, including during local development.

## What is generated

| Item | Published path | Purpose |
| --- | --- | --- |
| Home | `/` | Site title, description, WebSite/WebApplication JSON-LD and crawlable introduction |
| Fusion dex | `dex.html` | Search and filtering entry |
| Triple overview | `triples.html` | Supported triples and crawlable links |
| Dual fusion | `fusion/1.4.html` | Head/body names in English, Korean and Japanese, types, six base stats and BST before JavaScript loads; then the normal interactive lab |
| Triple fusion | `triple/1.4.7.html` | Official combination, sprite and dedicated stats; then the interactive triple lab |
| Human-readable index | `fusions/`, `fusions/1.html` | Head → body → individual combination links |
| Sitemap index | `sitemap.xml` | Links to `sitemaps/pages-N.xml`, at most 40,000 URLs each |
| Shared preview | `social/preview.jpg` | 1200 × 630 JPEG using an actual website screenshot |
| Icons | `favicon.svg`, `icons/*.png` | Existing FV mark in SVG and 96/180/192/512 pixel PNG sizes |
| Browser manifest | `site.webmanifest` | Name, icons and theme; no service worker or offline data cache |
| Missing page | `404.html` | Helpful navigation with `noindex,follow` |

With the current snapshot, the build includes **251,001 dual combinations, 23 triples and 505 overview/index pages**, for **251,529 canonical URLs**. These are combinations supported by this viewer's imported snapshot, not a claim about every Pokémon in the latest game version. A combination page does not imply a custom sprite exists; the viewer uses the game's autogenerated sprite when needed.

Pages are generated in `dist/` at build time; hundreds of thousands of generated files are **not** committed. Both names and stats come from the existing external database snapshots and the same fusion formula as the viewer. Update the database snapshots and rebuild to update search pages. The build reports its URL count and byte size in `dist/build-report.json` and fails above a 950 MB total output budget, below GitHub Pages' [1 GB published-site limit](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits).

## Canonical URL policy

- Each ordered pair has one canonical page. `fusion/1.4.html` and `fusion/4.1.html` are distinct.
- Sprite variants share the pair's canonical URL. Tags, artists, sorting and pagination do not create sitemap entries.
- Existing `?head=1&body=4#lab` and triple query links still work and become clean entry URLs in the viewer.
- A bare home visit keeps the home URL and generic site metadata while restoring the last view or picking a random fusion. Refreshing a shared combination always restores that explicit combination.
- Saved fusions are local browser data. The Saved view sets `noindex,follow`; no bookmark pages or local data are put in the sitemap.
- The default indexable language is English, with Korean/Japanese Pokémon names in the initial combination HTML. UI language switches are browser preferences; they are not separate `hreflang` URLs.

The initial HTML is the same for crawlers and people. There is no user-agent detection, automatic redirect, paid analytics or Indexing API integration.

## After deployment: Google

1. Finish the normal GitHub Pages deployment and confirm `sitemap.xml` and `fusion/1.4.html` return successfully on the production site.
2. In [Google Search Console](https://search.google.com/search-console/), add a **URL-prefix** property for `https://dominokorean.github.io/Pokemon-Fusion-Viewer/`. A Domain property for `github.io` would require DNS control you do not have.
3. Complete the ownership method offered by Google. If using an HTML verification file, put the **exact issued file** in `public/`. If using a verification meta tag, put the issued tag directly in `index.html`'s `<head>`, **outside** `<!-- SEO:START --> … <!-- SEO:END -->`. The build replaces that generated block. Do not invent a token or remove an existing issued verification tag.
4. Rebuild/deploy the verification file or tag, then finish verification.
5. Under Sitemaps, submit `sitemap.xml`, or its complete production URL. The index links all seven component sitemaps; do not submit 250,000 individual URLs manually.
6. Inspect the home page and one combination URL. Check the live HTML, selected canonical and crawl status. Request indexing for a small representative sample if useful.

Google's [sitemap documentation](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap) explains submission; [URL inspection/recrawl documentation](https://developers.google.com/search/docs/crawling-indexing/ask-google-to-recrawl) covers individual requests. Discovery, indexing and ranking are separate decisions. Submission does not guarantee every combination will be indexed.

## Bing and Naver

- [Bing Webmaster Tools](https://www.bing.com/webmasters/): add/verify the site, or import the verified Search Console property, then submit the same `sitemap.xml`. See [verification methods](https://www.bing.com/webmasters/help/add-and-verify-site-12184f8b) and [sitemaps](https://www2.bing.com/webmasters/help/sitemaps-3b5cf6ed). Issued verification files belong in `public/`; meta tags belong outside the generated SEO block in the root HTML.
- [Naver Search Advisor](https://searchadvisor.naver.com/): use the site URL/property scope accepted by Naver, verify ownership and submit the sitemap URL. If the service requires control over the origin root rather than this repository subpath, complete that step from the `dominokorean.github.io` repository or a custom domain you control. Do not replace this repository's canonical URL merely to satisfy a verification form. [Naver ownership verification](https://searchadvisor.naver.com/guide/faq-start-register) reads the delivered HTML and does not execute JavaScript.

No account verification or external sitemap submission has been performed by the build.

## Important: robots.txt on a project site

Search engines read robots rules from **`https://dominokorean.github.io/robots.txt`**, at the domain root. This repository publishes under `/Pokemon-Fusion-Viewer/`, so its `robots.txt` at that subpath is **not authoritative crawler policy**. Submit `sitemap.xml` directly in webmaster tools. If you control the separate `dominokorean.github.io` repository, add this sitemap's absolute URL to its root robots.txt while preserving the rules for your other sites. With a custom domain served at its root, the included file can serve as the root robots.txt after updating the public URL. See [Google's placement rules](https://developers.google.com/crawling/docs/robots-txt/create-robots-txt).

Robots exclusions are not used as access control. The public site contains no private bookmark data.

## Preview artwork and descriptions

`social/preview.html` is the editable HTML/CSS source for the social card and is marked `noindex`. `social/website.jpg` is a screenshot of the real Regigigas × Volcarona lab. To refresh the card, update that screenshot, render `social/preview.html`, and capture its 1200 × 630 card region into `social/preview.jpg`. Keep the output dimensions consistent with the metadata and avoid changing artist-owned sprites.

The site description emphasizes the three main features: **mobile viewing, stat change comparisons and easy search**. Combination summaries add the ordered parents, fusion ID, type and database-derived base stats. Open Graph and `summary_large_image` metadata prepare shared links; the preview image is common to the site, not a newly generated image of each combination.

Search engines choose their own displayed [title/snippet](https://developers.google.com/search/docs/appearance/snippet) and images. Open Graph prepares sharing; it does not force a Google search thumbnail. The footer is marked `data-nosnippet` so community policy/support text does not become the main search summary. There are no fake reviews, ratings, affiliations or guaranteed rich-result claims.

## Validation and maintenance

```sh
npm test
npm run verify-data
npm run build
npm run verify-search
```

The build takes longer than the earlier SPA-only build because it writes all combinations. It runs `verify-search` automatically; that command can also recheck the existing output. Open an individual path with `npm run dev`; the development server renders it on demand without first generating 250,000 files. Check a reversed pair, a variant URL, a legacy query URL, browser Back/Forward, a triple and the home page. Review `dist/build-report.json` before deploying. Search pages and sitemaps are deterministic; no false `lastmod` timestamps are generated on every build.

When changing the host, update `SITE_URL` in `src/seo.mjs`, `public/robots.txt`, `public/404.html`, README links and the visible address in `public/social/preview.html`, then refresh the card. Rebuild and register the new sitemap/property with the relevant search engines. Generated canonical URLs and metadata must always point to the intended production host.
